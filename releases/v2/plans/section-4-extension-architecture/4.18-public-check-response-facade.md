## 1. Objective

Make the public **check-response façade** a first-class, synchronous V2 core contract: evaluate
one Rule **or** one Check Set against a record, in **user mode**, in **bulk**, with a
**Flow-invocable** wrapper, returning the normalized result model with a **contract version** and
**additive-only** growth. This is the synchronous counterpart to the asynchronous lifecycle
events — it returns a structured result in the caller's transaction.

## 2. Current state (verified)

`force-app/main/default/classes/RecordHealthCheck.cls` is the current façade. It provides:

- `RecordHealthCheck.run(configName, checkDeveloperName, recordId)` and a `runId` overload
  (`RecordHealthCheck.cls:25`, `:37`).
- **Single Rule only** — it evaluates one check by developer name against one record.
- `public with sharing`, user-mode by delegation to `RecordHealthCheckEngine` (which runs
  `WITH USER_MODE`).
- Correlated by a generated `runId`; logs `RUN_INVOKED` / `RUN_COMPLETE`.
- Tested by `RecordHealthCheckFacadeTest`.

## 3. Design (from `§4.18`)

- **Granularity.** One Rule or one Check Set against a record. Rule-level granularity gives the
  reuse benefit of a shared rule without a junction object (`§8`: junction object deferred; reuse
  via the façade). The Rule keeps its required parent Check Set for authoring.
- **Bulk.** Accept a record-Id list, return one response per record — so a consumer can evaluate
  across a list view without per-record calls. Bulkify: load config once, batch describe/SOQL.
- **Execution.** User mode. The caller's CRUD/FLS governs field access; the response reflects
  exactly what the caller is authorized to see (ties to [2.11](../section-2-metadata-contract/2.11-fls-presentation-completion.md)).
- **Return shape.** The normalized model already produced for the LWC:
  - **Rule response:** status, failure severity, reason code, check title, resolved failure/fix
    messages, found/expected values (subject to authorization), action label/URL.
  - **Check Set envelope:** overall status, outcome counts, and the per-Rule response list.
- **Declarative access.** A Flow-invocable wrapper over the **same** façade (many admin consumers
  are declarative-first). Map to/from bulk-safe DTOs.
- **Stability.** Response carries a contract version and grows additive-only. Keep the surface
  intentionally small so it can later become a packaged `global` contract without redesign.

## 4. Implementation plan

1. **Add a Check Set entry point.** `RecordHealthCheck.runSet(configName, recordId[, runId])`
   returning a Set envelope DTO (reuse the normalized model the LWC controller already builds —
   see `RecordHealthCheckController` / `RecordHealthCheckDefinitionResponse`). Do not duplicate
   normalization logic; call the same engine/service seam the controller uses.
2. **Add bulk overloads.** `run(configName, checkDeveloperName, List<Id> recordIds)` and
   `runSet(configName, List<Id> recordIds)` returning `List<...>` (one response per input Id,
   order-preserving). Load config once; avoid per-record SOQL/describe (bulkification is a hard
   requirement — `§4.14`, `§4.18`).
   - **Cap the batch size.** Define an explicit maximum records-per-call (mirror Flow's 200-record
     bulk unit) and reject or document behavior beyond it, so "evaluate across a list view" can
     never become an unbounded, limit-blowing request. The cap is part of the documented contract.
3. **Formalize the response contract version.** Add a `contractVersion` to the response envelope
   (and document additive-only growth). Publish the surface as **pre-1.0** until it stabilizes
   (`§4.18`), and tell consumers it may change.
4. **Flow-invocable wrapper.** Add an `@InvocableMethod` class with a request DTO and a response
   DTO mapping the normalized model. Salesforce-specific rules that must be honored:
   - **`@AuraEnabled` does not make a class Flow-visible.** `RecordHealthCheckResult` is already
     `@AuraEnabled` (good for the LWC) but Flow only sees fields annotated `@InvocableVariable`.
     Build a **dedicated Flow request/response DTO** with `@InvocableVariable` fields (label +
     description in plain admin language) rather than exposing `RecordHealthCheckResult` directly —
     this also decouples the Flow contract from the internal model so it can grow additively.
   - **Bulk contract is index-aligned.** `@InvocableMethod` receives a `List<Request>` and must
     return a `List<Response>` **the same size and order** (element _i_ of the output corresponds
     to element _i_ of the input). Flow invokes in bulk; a per-element loop that calls SOQL is a
     governor-limit failure — load config once and evaluate the batch.
   - Exactly **one** `@InvocableMethod` per class; give it a clear `label` and `category`.
   - Return the Set envelope or the single-Rule response per the request shape; do not return
     internal evaluator objects.
5. **Confirm user-mode + FLS parity.** Every new path runs user mode and honors the
   [2.11](../section-2-metadata-contract/2.11-fls-presentation-completion.md) FLS policy
   identically to the LWC (parity test).
6. **Reason codes.** Responses carry stable [2.9](../section-2-metadata-contract/2.9-reason-code-catalog.md)
   reason codes; consumers key on status/reason/severity/identity, never display text (`§4.18`).
7. **Packaging visibility (deferred decision).** Be precise about what `public` buys today:
   - Within the **same namespace** (source deploy, or an unlocked package with no namespace where
     everything lives in the default namespace), a `public` façade is already callable by
     admin/consumer Apex — that covers the initial OSS/source-deploy audience.
   - **True cross-package** consumption (a separately packaged extension calling in) needs `global`
     **or** a shared namespace; `public` is _not_ visible across package boundaries. That is what
     the `§6`/`§4.15` unlocked-vs-managed decision unlocks.
   - Keep the surface minimal now so promotion to `global` is a visibility change, not a redesign.
     Do **not** make it `global` before that decision — a `global` signature can't change later.

## 5. Transaction budget (multidimensional — a 200-record cap is not enough)

**A record cap alone does not bound cost.** The real load is `records × active rules × the query
work each rule performs` (each rule may run a source query, a comparison query, and an
applicability count query, each with its own row limit and formulas). The façade must declare and
enforce a budget across **every** governor dimension, not just SOQL statement count:

| Dimension                   | Why it grows                                       | Budget/gate                                              |
| --------------------------- | -------------------------------------------------- | -------------------------------------------------------- |
| Records per call            | caller-supplied list                               | Hard max (e.g. 200); fail-fast above it                  |
| Active rules per Set        | Set configuration                                  | Known at load; factor into the estimate                  |
| Configured queries per rule | source + comparison + applicability                | Count them up front; this is the real multiplier         |
| SOQL query rows (50k)       | records × rules × per-query row limits             | Estimate `Σ MaxQueryRows`; reject/degrade before running |
| CPU time (10s sync)         | formulas + comparison work per rule                | Measure in the capacity spike; cap synchronous scope     |
| Heap (6MB sync)             | response size = records × rules × per-rule payload | Bound response size; stream/paginate if needed           |
| Response size               | serialized envelope                                | Cap and document the max                                 |

- **Fail-fast validation.** Estimate the cost from `records × active rules × configured query work`
  **before** executing and reject over-budget requests with a clear, stable error — do not start a
  run that will die mid-way at a governor limit.
- **Recommend async beyond the envelope.** When a caller's scope exceeds the synchronous budget,
  the documented answer is Batch/Queueable (or the scheduled-assessment adapter, `§4.11`), not a
  larger synchronous call. The façade is for interactive/bounded use.
- **Bulk-safe:** no SOQL/DML/describe inside per-record loops (`§4.14`); load config once.
- **User mode** always; never widen to system mode to make a check "work" (`§1.5`).
- **Additive-only** response contract; version it; never repurpose a field.
- **Smallest surface.** Expose only what a consumer needs; do not expose internal evaluator
  classes (`§4.11` REST/API wrapper: "no exposure of internal evaluator classes"; `§4.7`).
- **No CS jargon** in DTO field names, `@InvocableMethod`/`@InvocableVariable` labels, or docs.
- One source of truth for normalization — reuse the LWC controller's model builder; do not fork it.

## 6. Acceptance criteria

**Test mechanics:** assert bounded growth, not a flat count. Wrap the bulk call in
`Test.startTest()`/`Test.stopTest()` and assert each governed dimension stays **within budget** as
`records × rules × queries-per-rule` scales — `Limits.getQueries()`, `Limits.getQueryRows()`,
`Limits.getCpuTime()`, `Limits.getHeapSize()`, and serialized response size. "Flat query count" is
the wrong assertion: query count _does_ grow with configured query work; the requirement is that it
stays **under the declared budget** and that over-budget requests fail fast. Use
`RecordHealthCheckTestDataFactory` and `System.runAs` for the FLS-parity user; extend
`RecordHealthCheckFacadeTest`.

- [x] `runSet` returns the full Set envelope (overall status, outcome counts, per-Rule list).
- [x] Bulk overloads return one response per input Id, order-preserving, and stay within the §5
      budget for a realistic worst case (N records × M rules × multiple configured queries).
- [x] **Fail-fast test:** an over-budget request (records × rules × query work beyond the envelope)
      is rejected up front with a stable error, not a mid-run governor exception.
- [x] **Capacity evidence:** a recorded scratch-org capacity run at the documented worst case
      (feeds the `§9` capacity gate).
- [x] Flow-invocable wrapper works for single and bulk invocation; validate the supported
      `@InvocableVariable` types/annotations in the **release-target API version**, not just "200".
- [x] Response carries `contractVersion`; documented additive-only; published pre-1.0.
- [x] Façade and LWC return identical FLS/reason-code policy for identical input (parity test).
- [x] Surface is not `global` until the `§6`/`§4.15` packaging decision.

- Land [2.9](../section-2-metadata-contract/2.9-reason-code-catalog.md) and
