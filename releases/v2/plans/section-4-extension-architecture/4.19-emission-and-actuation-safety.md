## 1. Objective

Guarantee the product's core promise: opening a record automatically evaluates and displays
health **and does nothing else**. This plan encodes the `§4.19` safety model as **enforced,
tested invariants** on the emission build — not documentation. It exists so that emission can
never turn "viewing a record" into "starting an automation chain."

## 2. The principle (from `§4.19`, verbatim intent)

> Record Health Check automatically evaluates and displays record health. Page-load evaluations
> are observational and never publish result events. Rules may optionally present a user-initiated
> action link. Platform-event publication is disabled by default and limited to non-page-load
> execution contexts. Automatic remediation and subscriber behavior remain outside core and
> belong in explicitly installed extensions.

```text
Open record → checks run automatically → results display → nothing else happens
```

Diagnosis is automatic; **treatment requires intent.**

## 3. Current state (verified — findings doc Finding 3)

Nothing emits today. There are no events and no publish fields. Until [4.2](4.2-lifecycle-events-and-publish-fields.md)
is built, these are **design constraints to honor**, not current behavior. This plan is the guard
rail that ships _with_ 4.2 — the invariants must be true from the first line of emission code, not
retrofitted.

## 4. Invariants to enforce (from `§4.19` + findings Finding 3)

1. **On-load never publishes.** `RUN_ON_LOAD` evaluations **never** publish Rule Result events,
   regardless of switch state anywhere. "Default off" is not sufficient — an admin could flip a
   switch without realizing a busy record page would then emit at page-view frequency. Prohibit it
   by design.
2. **Switches gate only deliberately initiated contexts.** `PublishRunEvent__c` /
   `PublishResultEvent__c` apply only to: an explicit programmatic request through the public
   façade ([4.18](4.18-public-check-response-facade.md)); a scheduled/batch evaluation; and, where
   a product decides to allow it, an explicit user-initiated run. Never page-load.
3. **Both publish fields default `false`.** Installing/upgrading core publishes nothing.
4. **Recursion guard.** Stamp run origin; refuse/guard republication for runs that originate
   inside an event-subscriber execution context. Core must never enter
   `publish failure → diagnostic event → publish failure` recursion (`§4.4`).
5. **Publish-after-commit vs immediate** — resolve the `§6` open decision; **lean after-commit**
   for anything that can drive record creation (phantom-event risk on rollback — findings Finding 3).
6. **On-load publishes nothing — neither stream** (audit reconciliation). Page-load evaluation
   publishes **no** `Record_Health_Check_Rule_Result__e` **and no** `Record_Health_Check_Set_Run__e`.
   The earlier wording that allowed a "separately consented on-load `Set_Run__e` for adoption
   analytics" contradicted the headline zero-events test and is **removed**. If component-impression
   / adoption analytics is ever wanted, it is a **distinct, separately consented activity event**
   (e.g. a `COMPONENT_VIEWED` activity, `§4.10`) — **not** the `Set_Run__e` lifecycle event and
   **not** enabled by the publish switches. That is out of scope here and would be its own decision.
7. **Payload minimization + identity/data-classification defaults** per `§4.13`.
8. **The action link is not core actuation.** `ActionLabel__c`/`ActionUrl__c` present an optional,
   author-defined, user-initiated link that does **not** depend on result-event publication.
   Displaying or clicking it does **not** publish a Rule Result event. The link's destination owns
   whatever it does; that is the destination's contract, not core's.

### Honest limitation: the guarantee is strongest for the component, weaker for the façade

The "on-load never publishes" invariant is only as strong as the **source of the execution
context**. There are two cases, and the plan must not oversell the second:

- **LWC / component path (enforced):** core itself stamps the context as `RUN_ON_LOAD` for
  automatic page-load evaluation, so the short-circuit is guaranteed by core — a caller cannot
  spoof it.
- **Public façade path (contractual, trusted):** the façade evaluates in a **deliberately
  initiated** context by definition, but core learns the context _from the caller_. A careless or
  malicious integration could invoke the façade from an on-load code path and still get
  publication. Core cannot detect that a façade call originated from a page load.

Mitigations, not a false guarantee: (a) the façade defaults to a deliberately-initiated source and
does **not** accept a `RUN_ON_LOAD` value from callers (there is no caller-supplied "this is
on-load" input that would enable publication — the on-load path is core-internal only); (b)
document that embedding the façade in an on-load Apex/LWC path to emit per-view telemetry is an
unsupported anti-pattern; (c) the recursion/origin guard (invariant 4) still applies. State this
plainly rather than implying core can enforce intent it cannot observe.

## 5. Implementation plan (layer onto [4.2](4.2-lifecycle-events-and-publish-fields.md))

1. **Thread the execution context into the publisher.** The engine/run model must carry the
   invocation source (`RUN_ON_LOAD`, `FACADE`, `SCHEDULED`, `BATCH`, `USER_INITIATED`, …). The
   publisher reads it and short-circuits publication for `RUN_ON_LOAD` **before** consulting any
   switch. Inspect `RecordHealthCheckRunContext` / `RecordHealthCheckEngine` for the seam.
2. **Guard order:** context check (is this a publishable context?) → switch check (`§4.12` truth
   table) → recursion guard → publish. A non-publishable context returns immediately.
3. **Recursion guard implementation.** Stamp a run-origin marker; when a run originates inside a
   subscriber execution, refuse to republish (or require an explicit idempotency guard per `§4.11`).
4. **Publish mode.** Implement the `§6`-chosen mode; if after-commit, use a publish-after-commit
   path so a rolled-back transaction produces no phantom events.
5. **Fallback, never recursion.** On publish-enqueue failure, record via the bounded
   `RecordHealthCheckLogger` fallback; never publish another event to report the failure (`§4.4`).
6. **Observability of state.** Expose effective publication state in authorized diagnostics so
   admins distinguish "no activity" from "publication disabled" (`§4.12`).

## 6. Acceptance criteria (all must be tested, not just documented)

- [x] **On-load invariant test:** a `RUN_ON_LOAD` evaluation with **both** switches ON publishes
      **zero** events (Set Run and Rule Result). This is the headline safety test.
- [x] **Context-gate test:** the same Check Set/Rule invoked through the façade with switches ON
      publishes per the `§4.12` truth table.
- [x] **Default-off test:** a fresh install (no switch changes) publishes nothing from any context.
- [x] **Recursion-guard test:** a run initiated from inside a subscriber does not republish.
- [x] **Rollback test:** under the chosen publish mode, a rolled-back transaction produces no
      phantom Rule Result events (if after-commit) or behaves exactly as documented (if immediate).
- [x] **Action-link test:** displaying/clicking an action link publishes no Rule Result event.
- [x] **Result-unchanged test:** a forced publish failure leaves the returned result unchanged and
      does not recurse.

## 7. Constraints

- These invariants are **security/safety boundaries** and may not be weakened to pass a test
  (`§1.5`). The on-load invariant in particular is non-negotiable.
- No new metadata, modes, or required admin decisions are introduced by the safety model itself
  (`§4.19`): the safety story rides on the existing switches + execution context.
- No CS jargon in any surfaced source/phase/label value.

## 8. Relationship to 4.2

[4.2](4.2-lifecycle-events-and-publish-fields.md) **builds** the events and publisher; **this
plan is the acceptance gate** that the build enforces the safety model. Treat them as one change
set: emission does not ship unless every invariant test here passes.
