## 1. Objective

Build the **two** core-owned lifecycle platform events and their opt-in publish fields, so the
ecosystem gets result and run telemetry without any per-plugin event type or engine branch:

1. `Record_Health_Check_Set_Run__e` — one Check Set **run** (component/façade use).
2. `Record_Health_Check_Rule_Result__e` — one finalized **Rule** result, carrying `RunId__c`.

Fifty plugins consume the same two streams (`§4.10`, `§4.17`); the event-type count stays two.

> **Gate:** This plan does not start until `§6` records the decision that lifecycle events ship in
> the initial V2 release (vs a later extension milestone) and picks **Publish Immediately vs
> Publish After Commit** (`§4.2`, `§6`). Until then, the [4.19](4.19-emission-and-actuation-safety.md)
> rules are a design constraint, and nothing emits.

## 2. Current state (verified — findings doc Finding 3)

- **None of it exists in `force-app/main`.** No `Record_Health_Check_Set_Run__e`,
  `Record_Health_Check_Rule_Result__e`, or `Record_Health_Check_Diagnostic__e`.
- No `PublishRunEvent__c` / `PublishResultEvent__c` fields on the CMDT.
- The only platform event in the repo is the archived, deferred
  `force-app/deferred/capture-metrics/objects/Record_Health_Check_Metric__e` (V1 capture-metrics,
  superseded per `§8`; retained for restoration reference only).

## 3. Scope of this plan

Three buildable pieces. The future `Record_Health_Check_Diagnostic__e` (`§4.4`) is **deferred**
until two credible diagnostic consumers exist — it is **out of scope** here.

> **Ship minimal first, grow additively — do not freeze the full ~20-field schema on day one.**
> The `§4.10`/`§4.2` field tables below are the _design target_, not the V1 payload. The release
> plan itself (`§4.8`) requires validating the schema with a **materially different second
> consumer** before freezing V1. So V1 ships the **core-identity subset** every consumer needs and
> adds fields additively as real consumers prove the need:
>
> - **Rule Result V1 minimum:** `ContractVersion__c`, `EventId__c`, `RunId__c`,
>   `CheckSetDeveloperName__c`, `RuleDeveloperName__c`, `Status__c`, `ReasonCode__c`, `Severity__c`,
>   `OccurredAt__c`, `Source__c`, `CoreVersion__c`, `ContainsRestrictedDetail__c`.
> - **Set Run V1 minimum:** `ContractVersion__c`, `EventId__c`, `RunId__c`, `Phase__c`,
>   `CheckSetDeveloperName__c`, `OccurredAt__c`, `Source__c`, `CoreVersion__c`, the outcome counts.
>
> Record/user identity, dependency linkage, durations, and session correlation are **additive
> follow-ons** gated by the `§4.13` identity/privacy policy and a proven consumer — not V1
> defaults. Adding a platform-event field later is non-breaking; removing one is breaking, so err
> toward too few.

### 3.1 Additive CMDT publish fields (`§2.1`, `§2.2`, `§4.12`)

| Field                   | Object                          | Type / default    | Purpose                                                                |
| ----------------------- | ------------------------------- | ----------------- | ---------------------------------------------------------------------- |
| `PublishRunEvent__c`    | `Record_Health_Check_Set__mdt`  | Checkbox, `false` | Publish `Record_Health_Check_Set_Run__e` for this Check Set            |
| `PublishResultEvent__c` | `Record_Health_Check_Rule__mdt` | Checkbox, `false` | Publish `Record_Health_Check_Rule_Result__e` after this Rule finalizes |

- Both default `false` — installing/upgrading core publishes nothing (`§4.12`).
- The two are **independent** (`§4.12` truth table): Off/Off = nothing; On/Off = Set Run only;
  Off/On = Rule Result only (still carries `RunId__c`, no Set envelope); On/On = both, correlated.
- Rule publication does **not** inherit from the Set checkbox.
- Adding `PublishRunEvent__c` takes the shipped Set schema to **12** fields; `PublishResultEvent__c`
  takes the Rule schema to **41**. Each requires contract, layout, permission, deployment,
  help-text, and test verification (`§2.1`, `§2.2`).

### 3.2 `Record_Health_Check_Set_Run__e` (`§4.10` run lifecycle)

Run phases: `STARTED`, `COMPLETED`, `CANCELLED`, `FAILED_TO_START`. **Design-target** fields per
`§4.10` (V1 ships the minimal subset above) —
including `ContractVersion__c`, `EventId__c`, `RunId__c`, `Phase__c`, `OccurredAt__c`,
`CheckSetDeveloperName__c`, `RecordId__c`/`ObjectApiName__c` (policy-gated), `InvokedByUserId__c`,
`OnBehalfOfUserId__c`, `Source__c`, `ClientSessionId__c`, the count fields (`EligibleRuleCount__c`,
`EvaluatedRuleCount__c`, `PassedCount__c`, `FailedCount__c`, `SkippedCount__c`, `UnableCount__c`,
`SystemErrorCount__c`), `DurationMs__c`, `DiagnosticsEnabled__c`, `CoreVersion__c`, `ReasonCode__c`.

- Count fields must reconcile with the finalized result collection (`§4.10`).
- `SkippedCount__c` treatment follows the [2.10 decision](../section-2-metadata-contract/2.10-skip-and-not-applicable-semantics.md)
  (a separate `NotApplicableCount__c` only if Option B is chosen).

### 3.3 `Record_Health_Check_Rule_Result__e` (`§4.2`, `§4.10` rule lifecycle)

One event per finalized Rule outcome, carrying `RunId__c`. **Design-target** fields per the `§4.2`
table (V1 ships the minimal subset above) —
`ContractVersion__c`, `EventId__c`, `RunId__c`, `EvaluationId__c`, `ParentEvaluationId__c`,
`OccurredAt__c`, `CheckSetDeveloperName__c`, `RuleDeveloperName__c`, `RecordId__c`/`ObjectApiName__c`
(policy-gated), `Status__c`, `Severity__c`, `EvaluatorType__c`, `DurationMs__c`, `ReasonCode__c`,
`InvokedByUserId__c`, `OnBehalfOfUserId__c`, `Source__c`, `CoreVersion__c`, `ContainsRestrictedDetail__c`.

- `Status__c`/`ReasonCode__c` use the [2.9](../section-2-metadata-contract/2.9-reason-code-catalog.md)/[2.10](../section-2-metadata-contract/2.10-skip-and-not-applicable-semantics.md)
  contracts. `ContainsRestrictedDetail__c` aligns with the [2.11](../section-2-metadata-contract/2.11-fls-presentation-completion.md)
  suppressed-detail flag.
- **Excluded by default** (`§4.2`, `§4.4`): messages, raw queries, formula source, Apex JSON,
  found/expected values, stack traces, action URLs, session IDs, tokens. Payload defaults to
  metadata identifiers + outcome data, not business record content.

## 4. Implementation plan

0. **Scratch-org spike first (prerequisite).** Before adopting the publish-after-commit convention
   and the event-test recipe project-wide, run a **minimal deployable spike** in a scratch org that
   proves: (a) publish-after-commit does **not** deliver events from a rolled-back transaction;
   (b) which assertions are possible in an **Apex test** (`Test.getEventBus().deliver()`) versus
   which require an **org-level integration test** across a real commit boundary. Record the result
   in an [audit](../../audits/); it decides the test conventions the rest of this plan relies on.
1. **Confirm the `§6` gate** (events ship in V2?) and the publish-mode decision. Record both.
2. **Add the two CMDT publish fields** (§3.1), and separate the three distinct permission concepts
   — do **not** conflate them under "permission sets (read for admins)":
   - **CMDT configuration visibility** — who can _see/author_ `PublishRunEvent__c` /
     `PublishResultEvent__c` in Setup (custom-metadata-type access), an admin-authoring concern.
   - **Apex/custom-permission access** — whether a caller may invoke the façade or pass the
     diagnostics gate (custom permission), unrelated to the CMDT fields.
   - **Platform-event object permissions** — subscribers need **Read**, publishers need **Create**
     on `Record_Health_Check_Set_Run__e` / `Record_Health_Check_Rule_Result__e`; these are
     event-object permissions, **not** record-object FLS and not the same as CMDT visibility.

   Update page layouts, help text, and the field-migration/size reference; add validator awareness
   if needed. Do not assume ordinary record-object FLS semantics apply uniformly to all three.

3. **Define the two platform events** (§3.2, §3.3) with `UPPER_SNAKE_CASE` value fields where
   applicable, `ContractVersion__c` on each, and `EventId__c` as the idempotency key.
   - **`publishBehavior` is metadata, not just code.** "Publish Immediately" vs "Publish After
     Commit" is the `publishBehavior` property on the **platform-event definition** (`.object-meta.xml`),
     resolved from the `§6` decision — set it there, don't try to emulate it only in Apex. (4.19
     leans After Commit for anything that can drive record creation.)
   - Use **High-Volume** platform events (the standard/default); note this in deployment guidance.
4. **Build the lifecycle publisher — batch per lifecycle point, not per transaction.** One
   internal seam that contains **no** extension-specific branches (`§4.10`). The earlier "single
   publish list per transaction" was wrong: a run has **multiple publish points** (a `STARTED`
   phase early, then completion + Rule Results at the end), so the rule is **bulk publish within
   each point** (one `EventBus.publish(List)` per point), not one list for the whole transaction.
   Define precisely:
   - **Chunking.** When the events at a point exceed the platform per-call event limit, publish in
     chunks; the chunk size is a documented, tunable constant, not unbounded.
   - **Partial-failure handling.** `EventBus.publish(List)` returns a `List<Database.SaveResult>`;
     inspect **each** result. Some events in a batch can fail while others succeed. Handle the
     failures (fallback log + optional idempotent retry keyed on `EventId__c`); never assume
     all-or-nothing.
   - **Allocation/limit exhaustion.** When the transaction DML budget or the hourly publish
     allocation is exhausted, degrade per an explicit policy (stop publishing, log via the
     `RecordHealthCheckLogger` fallback) — **never** silently drop audit-relevant events without a
     recorded signal (`§4.17`).
   - **Best-effort, no recursion.** A publish failure never changes the returned health-check
     result (`§4.2`, `§4.14`) and never recurses into another event (`§4.4`).
   - **DML/allocation reality.** `EventBus.publish` counts toward DML limits and hourly event
     allocations; a bulk façade run (N records × M rules) can generate N×M events — treat the
     per-transaction event count as a governed number bounded by the [4.18](4.18-public-check-response-facade.md)
     budget.
   - **Decide `STARTED`'s value.** `STARTED` only carries real-time value for **asynchronous/
     long-running** invocations (batch/scheduled) that span multiple transactions. For a
     **synchronous** run, `STARTED` and `COMPLETED` are both known at the end, so a "live" started
     event is illusory under publish-after-commit. Decision to record in `§6`: either omit
     `STARTED` for synchronous runs (emit `COMPLETED`/`FAILED_TO_START` only) or emit both at
     completion, explicitly documented as not-live. Do not imply real-time semantics the platform
     cannot provide.
5. **Enforce the [4.19](4.19-emission-and-actuation-safety.md) invariants from day one** —
   especially: `RUN_ON_LOAD` never publishes Rule Result events; switches gate only deliberately
   initiated contexts; recursion guard on runs originating inside a subscriber.
6. **Wire publication to the switches** exactly per the `§4.12` truth table; expose effective
   publication state in authorized diagnostics so admins can distinguish "no activity" from
   "publication disabled" (`§4.12`).
7. **Identity/data minimization** per `§4.13` — default to the minimal telemetry profile; Record
   ID / user identity only under the policy decided in `§6`.

## 5. Constraints / best practices

- **Two event types, forever** (`§4.10`, `§4.17`) — a plugin never adds `Slack_Event__e` etc.
  Adding a third core event requires the `§4.17` architectural-review conditions.
- **Consumers assume at-least-once, duplicates, opaque replay IDs, no ordering** (`§4.2`). Use
  `EventId__c`, never Replay ID, for idempotency. Subscribers must be bulkified.
- **Publish consumes platform allocations** — measure worst-case Rules/run, bulk runs, dependency
  evaluations, batch sizes (`§4.14`, `§4.17` capacity model). Keep edition-specific allocation
  numbers in deployment guidance, not hard-coded in the contract.
- **No CS jargon** in field labels, picklist labels, or `Source__c`/`Phase__c` values.
- Machine keys are stable status/reason/identity fields, never labels or messages (`§4.16`).

## 6. Acceptance criteria

**Test mechanics (Salesforce platform-event specifics):**

- **The recipe below is provisional until the step-0 spike confirms it** — Apex-test event
  mechanics are release-sensitive; do not treat them as proven conventions before the spike.
- Deliver events in tests with `Test.getEventBus().deliver()` after `Test.stopTest()` — events
  do not fire to subscribers synchronously; a test that just publishes and asserts will see nothing.
- Inspect **each** `Database.SaveResult` in the returned `List` (enqueued ≠ delivered — `§4.2`);
  a failed enqueue must leave the health-check result unchanged (assert both). Cover **partial**
  batch failure (some succeed, some fail), not just all-or-nothing.
- For **publish-after-commit**, prove a rolled-back transaction publishes **no** event — via the
  step-0 org integration test if an Apex savepoint test cannot exercise a true commit boundary.
- **Chunking test:** a batch exceeding the per-call event limit publishes in bounded chunks and
  every event still lands (or is accounted for in the fallback).
- Bulk: publish for N records × M rules and assert the publish is per-lifecycle-point-bulk (one
  `publish(List)` per point), not per-record, and within the [4.18](4.18-public-check-response-facade.md) budget.
- Use `RecordHealthCheckTestDataFactory` for config/records; assert on stable
  `Status__c`/`ReasonCode__c`/`EventId__c`, never on labels.

**Note on `ContainsRestrictedDetail__c`.** The event flag is acceptable — events are opt-in,
authorized, operator-facing telemetry, not the user-facing response the [2.11](../section-2-metadata-contract/2.11-fls-presentation-completion.md)
prohibition covers. Even so, the event still **excludes** the restricted values themselves by
default; the flag signals presence to an authorized subscriber, and diagnostics-only reason codes
follow the same visibility rule as the response.
