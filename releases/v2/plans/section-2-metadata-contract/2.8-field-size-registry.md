## 1. Objective

Generate **one authoritative size registry** from the shipped metadata that states, for **every**
custom field, its storage type, stored maximum, post-resolution maximum, and truncation/error
behavior — and make runtime, validators, help text, and extension contracts all reference the
same limits. Today the sizes exist in metadata but are not consolidated or reconciled.

## 2. Current state (verified)

- Field storage types and sizes are implemented in shipped metadata under
  `force-app/main/default/objects/Record_Health_Check_Rule__mdt/fields/` and
  `.../Record_Health_Check_Set__mdt/fields/`.
- `§2.8` records the current reality: `CheckDescription__c` and `CardSubtitle__c` use `Text(255)`
  (because Salesforce Long Text Area starts at 256), and larger Long Text Area fields back
  unbounded configuration (messages, formulas, SOQL, JSON, list expressions).
- The two-tier proposal (2,048 for human-readable long text/URLs, 8,192 for
  formulas/SOQL/JSON/list expressions) was **considered but not the shipped reality** — the
  registry must be generated from shipped metadata, not from the proposal.

## 3. Deliverable: the size registry

A generated table (e.g. `docs/v2/reference/field-size-registry.md`) with one row per field:

| Column                      | Meaning                                                                                                                                       |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Object                      | Rule or Set CMDT                                                                                                                              |
| Field API name              | e.g. `SourceQuery__c`                                                                                                                         |
| Storage type                | Text / Long Text Area / Checkbox / Number / Picklist                                                                                          |
| Stored maximum              | Character limit as defined in metadata                                                                                                        |
| Post-resolution maximum     | Limit **after** merge-token/URL resolution (`§2.7`). Mark **N/A** for fields that never undergo resolution — do not invent a number for them. |
| Truncation / error behavior | Truncate, reject at validation, or reject at runtime                                                                                          |

Per `§2.8` the registry must in particular record:

- API names, aliases, class names, prerequisite developer names, summaries → bounded **Text**.
- `ActionLabel__c` → short **Text**.
- messages, formulas, queries, JSON, URL templates → documented limits.
- URL validation applied **after** token resolution, against the **resolved** length, not only
  the stored template length.
- character limits are **not** byte guarantees.

**Clarify what "formula" means here.** The formula-bearing fields (`PassConditionFormula__c`,
`ApplicabilityFormula__c`, display formulas, etc.) are **Text/Long Text Area fields that store
formula source** — they are _not_ Salesforce formula-type fields, and so are governed by the
field's storage length, not by the Salesforce formula compile-size limits (5,000 characters /
3,900 bytes). The registry records the **storage** limit; note the distinction so no one confuses
the two. Only fields that never resolve tokens get **N/A** in the post-resolution column.

## 4. Implementation plan

1. **Extract from shipped metadata.** Script a read of every `*.field-meta.xml` under both CMDT
   objects; capture `<type>`, `<length>` (Text) / `<length>` (Long Text Area), and field name.
   Emit the registry table. Prefer a small script under `releases/v2/tools/` (an existing tools
   dir is present) so the registry is regenerable, not hand-maintained.
2. **Classify post-resolution behavior.** For fields that undergo merge/URL resolution (`§2.7`
   display/URL/SOQL-binding fields), define the resolved-length limit and where it is enforced.
3. **Reconcile runtime + validators.** Confirm `RecordHealthCheckConfigValidator`,
   `RecordHealthCheckRuleValidator`, `RecordHealthCheckMetadataValidator`, and the runtime resolver
   (`RecordHealthCheckValueResolver`, `RecordHealthCheckSoqlTemplate`) use the **same** limits the
   registry documents. Fix any drift.
4. **Align help text.** Where inline help states or implies a limit, make it match the registry.
5. **Wire into release gate.** Add "size registry generated and reconciled" to the `§9` closeout
   ([Section 9 plan](../section-9-release-readiness/9-release-readiness-gates.md)).

## 5. Constraints / best practices

- **Generated, not hand-maintained** — one source of truth (`§3.7` principle: do not hand-maintain
  duplicate facts). Regenerate the registry from metadata; do not edit it by hand.
- Runtime, validators, help text, and extension contracts must use the **same** limits (`§2.8`).
- Enforce resolved-length limits after token resolution, not just stored template length.
- No CS jargon in help text or registry column prose.

## 6. Acceptance criteria

- [ ] Registry generated from shipped metadata, one row per field, all six columns populated.
- [ ] Regeneration is scripted and repeatable (checked into `releases/v2/tools/`).
- [ ] Validators/runtime enforce the documented limits; a test asserts a resolved value exceeding
      the post-resolution maximum is handled per the documented truncation/error behavior.
- [ ] URL fields validate against resolved length after token resolution.
- [ ] Inline help matches the registry; no drift.

## 7. Out of scope

Changing field sizes. This plan documents and reconciles the **shipped** sizes; a size _change_
would be a separate breaking-change decision.
