## 1. Objective

Decide, once and for the whole product, whether **Skipped** and **Not Applicable** are one
outcome or two, and lock the contract before any downstream artifact (UI labels, Apex statuses,
reason codes, lifecycle event schemas, observability, examples) is frozen. Renaming only the UI
is explicitly **not** acceptable (`§2.10`).

## 2. Why this is first

Every other outstanding contract references the terminal outcome set:

- The [reason-code catalog](2.9-reason-code-catalog.md) must map applicability gates and unmet
  prerequisites to a documented reason code, and the number of status buckets determines the
  code families.
- The lifecycle events (`§4.10`) carry `SkippedCount__c` / `Status__c`; a second status changes
  the run-envelope counts and the Rule `Status__c` enum.
- The examples repository (`§3.3`) must exercise "skipped/not-applicable" scenarios and cannot
  freeze fixtures until the status set is known (`§3.7` acceptance scenarios).

## 3. Current state (verified)

- `RecordHealthCheckResult.status` (`force-app/main/default/classes/RecordHealthCheckResult.cls:19`)
  documents the enum as: `PASS, FAIL, UNABLE_TO_EVALUATE, SKIPPED, ERROR`. **Today there is a
  single `SKIPPED` status — no separate `NOT_APPLICABLE`.**
- Applicability is driven by `ApplicabilityMode__c` and the prerequisite `PrerequisiteRule__c`
  (`§2.3`); the validator only requires the fields the selected mode uses.
- The LWC (`force-app/main/default/lwc/recordHealthCheck`) already distinguishes hidden-skipped
  vs hidden-success rows (`_isHiddenSkipped` / `_isHiddenSuccess`) and honors
  `SkippedChecksDisplay__c`.

## 4. The decision to make

Choose **exactly one** and record the owner, date, and rationale in `V2-RELEASE-PLAN.md §6`.

### Option A — One status (`SKIPPED`), differentiated by reason code (recommended default)

Keep the single `SKIPPED` status. Applicability-gate misses and unmet prerequisites are both
`SKIPPED`, distinguished by stable reason codes (e.g. `NOT_APPLICABLE_BY_FORMULA`,
`NOT_APPLICABLE_BY_COUNT`, `PREREQUISITE_NOT_MET`). Counts stay one bucket (`SkippedCount__c`).

- **Pros:** no schema/enum change; matches shipped code; simplest for consumers; reason code
  already carries the "why" per `§2.9` ("status is an outcome category; reason code explains why").
- **Cons:** consumers who want to report "not applicable" separately must filter on reason code.

### Option B — Two statuses (`SKIPPED` and `NOT_APPLICABLE`)

Introduce a distinct `NOT_APPLICABLE` terminal status. Must define (`§2.10` requirement):
the behavioral difference, the display treatment, and the count treatment (separate count field
on the run envelope, e.g. `NotApplicableCount__c`, or folded into `SkippedCount__c`).

- **Pros:** first-class reporting of "this check does not apply here" vs "this check was skipped
  for another reason."
- **Cons:** touches `RecordHealthCheckResult`, the LWC display logic, `SkippedChecksDisplay__c`
  semantics, every lifecycle count field, and every example fixture. Larger blast radius.

> Recommendation: **Option A**, unless a concrete consumer requirement proves two report-distinct
> buckets are needed. It honors the `§2.9` "status = outcome, reason code = why" separation and
> requires no enum change to shipped code.

## 5. Implementation plan (once decided)

### If Option A

1. Confirm `SKIPPED` is the only applicability-gate/prerequisite terminal status; document the
   decision in `§2.10` and `§6`.
2. Define the skip reason-code family in the [reason-code catalog](2.9-reason-code-catalog.md):
   at minimum `NOT_APPLICABLE_BY_FORMULA`, `NOT_APPLICABLE_BY_COUNT`, `PREREQUISITE_NOT_MET`.
3. Ensure the engine sets the correct reason code at each gate (search `RecordHealthCheckEngine`
   for applicability and prerequisite short-circuits). Reconcile with codes the engine **already
   emits** — `RECORD_NOT_ACCESSIBLE` (`RecordHealthCheckEngine.cls:413`) and the `SKIP_RECORD`/
   `SKIP` tokens in constants — so the skip family is a clean superset, not a parallel vocabulary.
4. Update the LWC to optionally surface the human reason for a skipped row (the `§2.10`
   disposition: "Surface skip reason and suppressed-row toggle in the LWC"). Presentation only —
   no evaluation change.
5. Update `SkippedChecksDisplay__c` inline help so it reads as "not run" without implying a
   separate status.

### If Option B

1. Add `NOT_APPLICABLE` to the status enum in `RecordHealthCheckResult` and every place the
   status set is validated/rendered (`RecordHealthCheckConstants`, engine, LWC status map).
2. Define the behavioral difference precisely: which gates produce `SKIPPED` vs `NOT_APPLICABLE`.
   Recommended mapping — applicability-mode misses → `NOT_APPLICABLE`; unmet prerequisite →
   `SKIPPED` (a prerequisite _could_ have run). Document it; do not leave it to interpretation.
3. Decide count treatment on the run envelope (`§4.10`): add `NotApplicableCount__c` or fold in.
   Keep it consistent with the LWC summary counts.
4. Add a display picklist value or reuse `SkippedChecksDisplay__c` for both; specify each.
5. Backfill reason codes for both statuses in the [reason-code catalog](2.9-reason-code-catalog.md).

## 6. Constraints

- Labels use plain admin language — "Not applicable" / "Skipped", never internal shorthand.
- Stored status/reason values are `UPPER_SNAKE_CASE`; UI shows sentence-case labels.
- Whatever is chosen must be applied consistently across: UI labels, Apex statuses, reason codes,
  lifecycle event schemas (`§4.10`), observability, examples, and help text (`§2.10`).

## 7. Acceptance criteria

- [x] Decision (A or B) recorded in `§2.10` and the `§6` decision list with owner + date.
- [x] `RecordHealthCheckResult` status documentation matches the decision.
- [x] Reason codes for applicability/prerequisite skips exist in the catalog and are set by the
      engine, covered by positive + negative Apex tests.
- [x] If Option B: not applicable because Option A was adopted.
- [x] No lifecycle event, façade response, or example fixture was frozen before this landed.

Building the lifecycle events themselves (that is [4.2](../section-4-extension-architecture/4.2-lifecycle-events-and-publish-fields.md));
