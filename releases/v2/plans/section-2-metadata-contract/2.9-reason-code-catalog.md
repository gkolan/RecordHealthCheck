## 1. Objective

Replace the free-text `reasonCode` with a **stable, enumerated, documented, tested** reason-code
registry so that consumers, the façade, the FLS policy, and future lifecycle events all key on
codes, never on display messages (`§2.9`: "reason code explains why; display messages are never
integration keys"; `§4.16`: machine logic uses stable status/reason/identity, never labels).
This is the small unblocking task called out in the findings doc — do it first.

## 2. Current state (verified)

- `RecordHealthCheckResult.reasonCode` (`force-app/main/default/classes/RecordHealthCheckResult.cls:49`)
  is a `String`, but it is **not empty in practice** — the engine already writes ad-hoc literal
  codes such as `RECORD_NOT_ACCESSIBLE` (`RecordHealthCheckEngine.cls:413`), and the constants file
  carries related tokens (`SKIP_RECORD`, `SKIP`). So the work is **rationalizing and centralizing
  existing codes**, not inventing a set from nothing. Grep `reasonCode =` across the classes first
  to inventory what is emitted today, then map each to a registry constant.
- `RecordHealthCheckConstants` already centralizes restricted value sets (severities, null/empty
  behaviors) as `UPPER_SNAKE_CASE` string sets — the reason-code registry follows the same shape
  and lives alongside them (or in a dedicated `RecordHealthCheckReasonCodes` class).
- Status enum documented at `RecordHealthCheckResult.cls:19`: `PASS, FAIL, UNABLE_TO_EVALUATE,
SKIPPED, ERROR`.
- **Keep `String`, not an Apex `enum`.** Reason codes must be additive-only and appear in
  serialized responses and (later) platform-event fields; an Apex `enum` is brittle across package
  versions and awkward to serialize/deserialize forward-compatibly. A validated `String` set gives
  the same safety with additive freedom.

## 3. Design

Reason codes are grouped into families aligned to terminal status. Codes are `UPPER_SNAKE_CASE`,
stable, and additive-only once shipped (never repurpose a code's meaning). Each code has: the
code token, the status it accompanies, a one-line meaning, and whether it may carry restricted
detail (ties to [2.11](2.11-fls-presentation-completion.md)).

### Where reason codes earn their keep

**Do not assign a reason code to a plain `PASS` or `FAIL`.** The `status` already carries that
outcome, and a `PASSED`/`FAILED` code is pure redundancy that adds noise to every response and
event. Reason codes exist to explain the **non-happy-path** outcomes — `SKIPPED`,
`UNABLE_TO_EVALUATE`, and `ERROR` — where "why" is not obvious from the status. So:

- `PASS` / `FAIL` → `reasonCode` is **null/absent** (status is sufficient).
- `SKIPPED` / `UNABLE_TO_EVALUATE` / `ERROR` → `reasonCode` is **required** and drawn from the
  registry.

### Proposed initial registry

> The skip family follows [2.10 Option A](2.10-skip-and-not-applicable-semantics.md): one `SKIPPED` status differentiated by reason code.

| Reason code                 | With status          | Visibility           | Meaning                                                                                                                                                                                                  |
| --------------------------- | -------------------- | -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NOT_APPLICABLE_BY_FORMULA` | `SKIPPED`            | normal               | Applicability formula evaluated false.                                                                                                                                                                   |
| `NOT_APPLICABLE_BY_COUNT`   | `SKIPPED`            | normal               | Applicability count operator/threshold not met.                                                                                                                                                          |
| `PREREQUISITE_NOT_MET`      | `SKIPPED`            | normal               | A prerequisite Rule did not pass.                                                                                                                                                                        |
| `INVALID_CONFIGURATION`     | `UNABLE_TO_EVALUATE` | normal               | Configuration is invalid (validator-class family).                                                                                                                                                       |
| `INVALID_FORMULA`           | `UNABLE_TO_EVALUATE` | normal               | Formula could not be parsed/evaluated.                                                                                                                                                                   |
| `INVALID_QUERY`             | `UNABLE_TO_EVALUATE` | normal               | Query syntax/binding/row-limit problem.                                                                                                                                                                  |
| `CANNOT_EVALUATE`           | `UNABLE_TO_EVALUATE` | **normal**           | **Neutral, non-disclosing** unable reason. This is what a normal-mode response returns when an FLS restriction blocks evaluation, so it is indistinguishable from other unable causes (`§2.11`).         |
| `RECORD_NOT_ACCESSIBLE`     | `UNABLE_TO_EVALUATE` | **diagnostics-only** | The **whole record** is not accessible (emitted today at `RecordHealthCheckEngine.cls:413`). Restriction-disclosing → appears only in the diagnostics-gated detail, never the normal response.           |
| `FIELD_NOT_ACCESSIBLE`      | `UNABLE_TO_EVALUATE` | **diagnostics-only** | A **single field** required to evaluate is not accessible (drives [2.11](2.11-fls-presentation-completion.md)). Distinct from `RECORD_NOT_ACCESSIBLE`. Restriction-disclosing → diagnostics detail only. |
| `NO_ROWS`                   | `UNABLE_TO_EVALUATE` | normal               | Query returned zero rows **and** `NoRowsResult__c = UNABLE_TO_EVALUATE`. When `NoRowsResult__c` maps zero rows to PASS/FAIL/SKIP, that terminal status wins and **no** `NO_ROWS` reason is emitted.      |
| `EMPTY_VALUE`               | `UNABLE_TO_EVALUATE` | normal               | Source value empty **and** `EmptyValueHandling__c = UNABLE_TO_EVALUATE`. When `EmptyValueHandling__c` maps empty to PASS/FAIL/SKIP, that status wins and no `EMPTY_VALUE` reason is emitted.             |
| `APEX_CHECK_EXCEPTION`      | `UNABLE_TO_EVALUATE` | normal               | Expected exception from an Apex check normalized by the contract.                                                                                                                                        |
| `SYSTEM_ERROR`              | `ERROR`              | normal               | Unexpected framework/engine failure (reserve `ERROR`/system language for this per `§1.2`).                                                                                                               |

**Visibility is part of the contract (audit fix).** Codes marked **diagnostics-only** are
restriction-disclosing and must **never** appear in a normal-mode response — the engine emits the
neutral `CANNOT_EVALUATE` in normal mode and swaps in the specific code only inside the
diagnostics-gated detail (`§2.11`). `RECORD_NOT_ACCESSIBLE` and `FIELD_NOT_ACCESSIBLE` remain
**distinct** so an authorized operator can tell whether the whole record or one field is the
problem.

**`NO_ROWS`/`EMPTY_VALUE` are not "configured" hand-waves.** Each is emitted **only** when the
corresponding handling field maps that condition to `UNABLE_TO_EVALUATE`. If the configuration
maps it to a terminal PASS/FAIL/SKIP, the outcome carries that status and no unable reason — the
mapping is precise, not a dual-status ambiguity. Freeze these two only after `NoRowsResult__c` /
`EmptyValueHandling__c` value sets are confirmed against shipped metadata.

Keep the free-text human explanation _separate_ from the code — the code is the integration key,
the message is presentation. Do not overload one field for both.

## 4. Implementation plan

1. **Create the registry.** Add `RecordHealthCheckReasonCodes` (or a `REASON_CODES` set +
   documented constants block in `RecordHealthCheckConstants`). Expose each code as a
   `public static final String` and a validation set, mirroring `VALID_SEVERITIES` style.
2. **Emit codes at every non-happy-path terminal in the engine.** Audit `RecordHealthCheckEngine`
   and each evaluator (`RecordHealthCheckFormulaEvaluator`, `RecordHealthCheckSoqlEvaluator`,
   `RecordHealthCheckCompareQueriesEvaluator`, `RecordHealthCheckApexEvaluator`) to set a registry
   code for `SKIPPED`/`UNABLE_TO_EVALUATE`/`ERROR` — no bare literals; reference the constants.
   Leave `reasonCode` null for `PASS`/`FAIL`.
3. **Normalize legacy values.** Anywhere `reasonCode` is set to an ad-hoc string, replace with a
   registry constant. Grep for `reasonCode =` across `force-app/main/default/classes`.
4. **Align the skip family** with the [2.10](2.10-skip-and-not-applicable-semantics.md) outcome.
5. **Mark and enforce visibility.** Tag each code `normal` or `diagnostics-only` in the registry.
   `RECORD_NOT_ACCESSIBLE` and `FIELD_NOT_ACCESSIBLE` are `diagnostics-only`; the engine emits the
   neutral `CANNOT_EVALUATE` in normal mode and substitutes the specific code only inside the
   diagnostics-gated detail ([2.11](2.11-fls-presentation-completion.md)). A helper (e.g.
   `RecordHealthCheckReasonCodes.isDiagnosticsOnly(code)`) keeps the rule in one place.
6. **Document.** Add a reason-code reference doc (e.g. `docs/reference/reason-codes.md`) generated
   from or synchronized with the registry. Docs and code agree in the same commit (`§1.5`).

## 5. Constraints / best practices

- Codes are `UPPER_SNAKE_CASE`, stable, additive-only. Never rename or repurpose after release.
- **No CS jargon in code names or docs** — codes describe outcomes in admin language, not
  internal mechanics. (This registry is a good place to lead by example ahead of the `§9`
  `scalar`/`comparator` cleanup.)
- The registry is the single source of truth; the LWC status map, the façade, and lifecycle
  `ReasonCode__c` all reference it.
- One code = one meaning. `status` = outcome bucket; `reasonCode` = why; message = presentation.
