## 1. Objective

Finish the field-level-security (FLS) presentation policy from `§2.11`: the normal response
degrades **without leaking** that a field is restricted, an authorized-diagnostics caller gets
the **honest** detail, and both are **enforced server-side**. This closes the `§6` FLS open item
for both the LWC and the façade; the only remaining item after is scratch-org verification of
`USER_MODE` formula-evaluation behavior.

## 2. Policy (from `§2.11`, do not re-derive)

> **Correction (design audit 2026-07-13).** An earlier version of this plan sent
> `containsRestrictedDetail = true` and the reason code `FIELD_NOT_ACCESSIBLE` to _normal_ callers.
> That is a **security contradiction**: the policy requires restricted and genuinely blank values
> to be **indistinguishable**, and a presence flag or a restriction-specific reason code reveals
> exactly the fact that must stay hidden. The rule below is the corrected contract:
> **the normal response carries neither restricted detail, nor a restriction-presence flag, nor a
> restriction-specific reason code. All three exist only inside the diagnostics-gated detail.**

- **Normal mode never announces a restriction — not in a value, a flag, or a reason code.** An
  inaccessible display value renders as a neutral empty value, indistinguishable from a genuinely
  blank value. No field API name, no "access"/"permission" wording, **no `containsRestrictedDetail`
  flag**, and **no `FIELD_NOT_ACCESSIBLE`/`RECORD_NOT_ACCESSIBLE` reason code**.
- **When an inaccessible field prevents evaluation** → outcome is **Unable to Evaluate** with the
  Rule's author-written `UnableToEvaluateMessage__c` and a **neutral, non-disclosing** reason code
  that is indistinguishable from other unable causes — not `FIELD_NOT_ACCESSIBLE`, not a raw
  permission error.
- **Diagnostics may be honest.** Only for an authorized admin with diagnostics active does the
  response carry the honest detail: the field name, the specific `FIELD_NOT_ACCESSIBLE` /
  `RECORD_NOT_ACCESSIBLE` reason code, and the presence flag.
- **Enforced server-side.** Core strips inaccessible fields **and** withholds the flag/specific
  reason code before returning; none of it reaches the browser in normal mode. The honest detail
  is assembled **only** when the caller passes the diagnostics gate.

## 3. Current state (verified in code — corrects the findings-doc summary)

`WITH USER_MODE` is enforced, but the behavior is **not** "inaccessible field renders blank." The
earlier summary (findings Finding 2: "an inaccessible field already yields no value; the LWC
renders null as blank") is **imprecise and must not be relied on.** Verified against the engine:

- **A field in the evaluation query throws — it does not blank.** `loadRecord(...)` runs the base
  query `WITH USER_MODE` (`RecordHealthCheckEngine.cls:398`); an inaccessible field raises an
  exception, which the engine catches and turns into `UNABLE_TO_EVALUATE` with reason
  `RECORD_NOT_ACCESSIBLE` and message "The record could not be accessed…" (`~:400–416`). So the
  normal-mode outcome for a query-referenced field is **Unable to Evaluate**, not a silent blank.
- **Two different code paths, do not conflate them:**
  - _Evaluation-input field_ (in the SOQL) → `USER_MODE` **throws** → Unable to Evaluate.
  - _Display-only value_ (formula/aggregate/derived, not in a `USER_MODE` query) → may render as
    a bare null; this is the only path where "renders blank" is true, and it is exactly the path
    `Security.stripInaccessible` should own (§4.2 below).
- **Concrete leak vector to close:** the catch block sets `detailMessage = ex.getMessage()`
  (`RecordHealthCheckEngine.cls:415`). A `USER_MODE` FLS exception message can contain the **field
  API name**. If `detailMessage` reaches the browser in normal mode, that is precisely the
  disclosure `§2.11` forbids. **Auditing `detailMessage` gating is a required step, not optional.**
- Field gates via `isAccessible()` exist (`~:1099, 1116, 1170`) and
  `RecordHealthCheckSoqlTemplate` forbids `SYSTEM_MODE` — both correct and retained.
- Existing ad-hoc codes (`RECORD_NOT_ACCESSIBLE`, etc.) predate the registry; reconcile them in
  [2.9](2.9-reason-code-catalog.md) rather than inventing parallel names.

**Gaps to close (the `§2.11` promises not yet implemented):**

1. **Distinguish record-level from field-level.** `RECORD_NOT_ACCESSIBLE` already exists for the
   whole-record case; add `FIELD_NOT_ACCESSIBLE` (via [2.9](2.9-reason-code-catalog.md)) for the
   single-field case. They are different facts and consumers need to tell them apart.
2. **Audit and gate `detailMessage`.** Confirm whether `detailMessage` crosses to the browser in
   normal mode; if it can, restrict raw `ex.getMessage()` to the diagnostics-gated admin detail
   only, and return a stable code + neutral message otherwise.
3. **Suppressed-detail flag lives ONLY in the diagnostics-gated detail** (audit fix). A consumer
   that legitimately needs to tell "genuinely blank" from "withheld by FLS" is an **operator using
   diagnostics**, not an ordinary caller. So `containsRestrictedDetail` is part of the
   diagnostics-only detail object, never a top-level field on the normal response.
4. **Neutral reason code in normal mode.** An FLS-blocked evaluation returns `UNABLE_TO_EVALUATE`
   with a **non-disclosing** reason (see [2.9](2.9-reason-code-catalog.md)) in normal mode; the
   specific `FIELD_NOT_ACCESSIBLE` / `RECORD_NOT_ACCESSIBLE` code appears only in the diagnostics
   detail.
5. **Diagnostics-gated honest detail** — when `showDiagnostics` is authorized, produce an
   admin-only detail object carrying the field name, the specific reason code, and the flag,
   generated **server-side only** when the caller passes the diagnostics gate.
6. **Confirm the normal-mode invariant end to end** across both the LWC and the façade response.

The diagnostics authorization gate already exists: `RecordHealthCheckConfigService` sets
`showDiagnostics = ShowDiagnostics__c && RecordHealthCheckAccess.canViewDebugDetails()` (findings
Finding 1). Reuse that same gate — do not invent a second authorization path.

## 4. Implementation plan

1. **Model the response as two tiers.** Keep the normal `RecordHealthCheckResult` free of any
   restriction signal. Add a **separate, nullable diagnostics-detail object** (e.g.
   `adminDetail`) that carries `containsRestrictedDetail`, the removed field name(s), and the
   specific reason code. This object is populated **only** when the diagnostics gate passes and is
   `null` otherwise — so there is no top-level flag to leak. (The event field
   `ContainsRestrictedDetail__c` in `§4.2` is operator-facing, opt-in telemetry and is a separate
   concern from this user-facing response.)
2. **Strip inaccessible display fields server-side.** In the engine's result-assembly path,
   before returning: for each display value (found/expected/display formulas/text), if the source
   field is inaccessible, blank the value. Never rely on the LWC to hide it.
   - **Prefer the platform mechanism.** Evaluate `Security.stripInaccessible(AccessType.READABLE, records)`
     with the returned `SObjectAccessDecision` (`getRemovedFields()`) as the primary way to remove
     unreadable fields from any SObject/records the response is built from — it is the
     Salesforce-recommended FLS-strip API and is currently **not used anywhere in the repo**
     (verified: no `stripInaccessible` in `force-app/`). The existing manual `isAccessible()`
     checks (`RecordHealthCheckEngine.cls` ~L1099/L1116/L1170) are correct but per-field and
     easy to miss on a new code path; `stripInaccessible` fails safe by default.
   - `stripInaccessible` sanitizes **SObjects only**. It does **not** sanitize already-derived
     strings, formula outputs, aggregate values, exception text (`detailMessage`), or resolved
     URLs. For every one of those non-SObject paths, keep the explicit `isAccessible()` gate on the
     underlying field and blank on inaccessibility. Step 5 (inventory) proves none is missed.
   - When a field is removed, record it into the **diagnostics-detail object** (step 4), never into
     the normal response.
3. **Map evaluation-blocking FLS to Unable-to-Evaluate with a neutral reason.** When an
   inaccessible field prevents the check from running (not just from displaying), set status
   `UNABLE_TO_EVALUATE`, the author's `UnableToEvaluateMessage__c`, and a **non-disclosing** reason
   code in normal mode (indistinguishable from other unable causes). The specific
   `FIELD_NOT_ACCESSIBLE` / `RECORD_NOT_ACCESSIBLE` code goes into the diagnostics-detail object.
4. **Produce diagnostics-only honest detail.** Populate the `adminDetail` object **only when** the
   `showDiagnostics` gate passes: field name(s), specific reason code, `containsRestrictedDetail`,
   and any raw `ex.getMessage()`. When the gate is not passed, `adminDetail` is `null` and nothing
   about the restriction — value, field name, flag, or specific code — is present in the payload.
5. **Complete source-to-response inventory.** Enumerate **every** field of the response and its
   data source — base SObject fields, related-record fields, formula outputs, query/aggregate
   values, author messages, resolved action URLs, and exception text — and prove each is neutral in
   normal mode. This is a required artifact, not an ad-hoc check (audit gap on the strip seam).
6. **Apply identically in the façade path.** [4.18](../section-4-extension-architecture/4.18-public-check-response-facade.md)
   returns the same `RecordHealthCheckResult`; verify the façade honors the same gate and strip.
7. **LWC render check.** Confirm the LWC never renders the admin detail unless
   `showDiagnostics` is set, and renders stripped values as neutral blanks.

## 5. Verification / acceptance criteria

**Test mechanics:** the normal-user vs authorized-admin split is exercised with `System.runAs`
against two users — one with, one without, the diagnostics custom permission and FLS to the
target field. (The suite uses `System.runAs` in **zero** files today; add a minimal-access user
via `RecordHealthCheckTestDataFactory`.) Wrap evaluation in `Test.startTest()`/`Test.stopTest()`
and assert on stable outcome fields, never on message text. Note the asymmetry: the **normal**
response must be asserted to _lack_ restriction signals; the **diagnostics** response is asserted
to _carry_ them.

- [ ] **Scratch-org `USER_MODE` formula-evaluation verification** (the `§6` open item on the
      `§4.18` critical path): a formula check referencing a field the running user cannot see
      resolves, **in normal mode**, to `UNABLE_TO_EVALUATE` with a **neutral** reason (not
      `FIELD_NOT_ACCESSIBLE`) — no leak, no raw exception; the specific code appears only under
      authorized diagnostics.
- [ ] Apex test: an inaccessible **display** field returns a blank value in normal mode with
      **no** `containsRestrictedDetail` flag and **no** restriction-specific reason code; the flag,
      field name, and specific reason appear **only** in the diagnostics-gated `adminDetail`.
- [ ] Apex test: an inaccessible **evaluation-input** field returns Unable to Evaluate + the
      author's `UnableToEvaluateMessage__c` + a neutral reason in normal mode; `FIELD_NOT_ACCESSIBLE`
      only under diagnostics.
- [ ] Apex test: an inaccessible **whole record** behaves the same — neutral in normal mode,
      `RECORD_NOT_ACCESSIBLE` (distinct from the field-level code) only under diagnostics.
- [ ] **Indistinguishability test:** for the same Rule/record, a _genuinely blank_ field and an
      _FLS-withheld_ field produce **byte-identical** normal-mode responses (no flag, code, or
      wording distinguishes them). This is the release-blocker acceptance.
- [ ] **`detailMessage` leak test:** the normal-mode response carries **no** `ex.getMessage()` /
      field API name; the raw detail appears **only** in the diagnostics-gated `adminDetail`.
- [ ] **Source-to-response inventory test:** every response field (SObject, related, formula,
      query/aggregate, message, resolved URL, exception text) asserted neutral in normal mode.
- [ ] Façade (`§4.18`) and LWC return the **same** policy for the same input (parity test).
- [ ] Jest: the LWC renders stripped values as blanks and never renders `adminDetail` when
      diagnostics off (it is `null` in the payload, not merely hidden).

## 6. Constraints / best practices

- **Enforced server-side** — the browser never receives a restricted value or field name in
  normal mode. This is a security boundary, not a UI convenience (`§1.5`: security may not be
  weakened to pass tests).
- Reuse the existing single diagnostics authorization gate; one authorization path only.
- Neutral degradation: a withheld value is indistinguishable from a blank value to an
  unauthorized user (revealing that a named field exists and is restricted is itself disclosure).
- No CS jargon in any surfaced message.
